# 至信链存证及客户核验方案

记录：2026-09-20。用户准备使用腾讯至信链，尚未取得存证回执。本文件是待实施方案，不代表已接入或已上链。

## 存证对象

二维码是访问入口。应存证审核发布后的某一批次版本内容及其公开图片，不是仅给二维码图片计算哈希。保留稳定入口 `/b/{批次编码}`，核验时明确具体发布版本，避免新内容沿用旧存证。

发布时保存不可变的原始 UTF-8 数据文件，并计算其 SHA-256。另保存图片清单，包含每个公开图片的相对路径、字节数及 SHA-256；按固定顺序和编码输出清单原始字节。生成版本化存证清单，包含批次、版本、发布主体、环境、数据摘要及图片清单摘要。计算清单原始字节的 SHA-256，作为拟提交的内容摘要。

最终提交格式、算法、字段和查询流程须以开通账户后取得的至信链 SDK/API 文档为准。若平台还提供另一种摘要，分别标明算法、对象和用途，不能混称交易哈希。发布文件、图片、清单一旦存证不得原位修改；变更产生新版本及新存证。

## 状态与回执

建议把“审核通过并正式发布一个版本”作为自动存证触发点。生成二维码本身不触发存证；草稿修改不触发存证。已有二维码和已发布页面可选择当前正式版本补做一次存证，不需重新制作二维码。

目标流程：管理员确认发布 → 固定该版本数据和图片 → 持久化待存证任务 → 后台自动提交至信链 → 自动查询和核对回执 → 更新该版本公开存证状态文件 → 页面自动显示存证结果。任务应可恢复、幂等，并定期补查已发布但遗漏任务的版本，不能依靠浏览器一直打开。

公开页面统一增加一个“区块链存证”组件，按当前显示的批次及版本读取独立状态文件。无需每次编辑 HTML 或粘贴哈希。链上交易哈希在提交后才产生，所以应放在这份独立状态文件中，不回写到已经计算内容摘要的原始版本数据。上链时客户已打开的页面可以定时查询状态，后续扫码则直接读取最新状态。

用户日常只需编辑、审核和发布。首次由开发完成平台接入、凭据配置和公共页面组件；异常时后台提供“查询结果／重试”操作。后续修改资料要发布新版本并另做存证，页面必须区分旧版本已存证和新版本待存证。以上自动流程尚未实现，不能把目前已经发布的页面误认为已自动上链。

- 未存证：尚未提交。
- 存证处理中：已发起但尚未取得并核对成功回执。
- 已上链：可信查询确认成功，且回执关联的内容摘要、版本、账户及链环境符合预期。
- 存证失败：平台明确拒绝或失败。
- 结果待确认：网络超时或查询暂不可用。先按业务幂等标识查询，不盲目重复提交。

保存平台原始回执、存证编号、交易哈希（平台提供时）、链环境、确认时间、内容摘要、算法以及核验结果。不得用本地 SHA-256、提交成功 HTTP 状态或随意填入的编号代替链上确认。管理员手工输入字段也不能直接变成“已上链”。

存证在发布后异步进行，失败不阻塞已发布页面。状态和回执展示文件独立于已哈希的版本文件，避免循环计算摘要。后端凭据不得进入浏览器、公开 JSON、Git 或日志。

## 二维码页面展示

真实回执验证通过后展示：

| 项目 | 展示内容 |
| --- | --- |
| 存证状态 | 已上链 / 处理中 / 未存证 / 结果待确认 |
| 存证平台 | 腾讯至信链及实际链环境；测试链明确标注 |
| 对应内容 | 批次编码、发布版本、确认时间 |
| 内容摘要 | 完整摘要及算法，提供复制按钮 |
| 交易哈希 | 平台实际返回的完整值，提供复制按钮；未提供则不虚构 |
| 存证编号 | 平台实际返回的编号 |
| 核验入口 | 经确认可用的官方入口；若需要权限，说明限制 |

提供“下载存证文件”“下载图片清单”“复制内容摘要”“查看核验说明”。只有取得明确的官方核验地址后才显示外部核验按钮，并校验 HTTPS 域名白名单。不根据交易哈希猜测区块链浏览器地址。

客户可下载原始存证文件，重新计算摘要，并与平台回执及权威查询结果对照；图片可按清单逐一计算摘要核对。本网站自查只能说明本地数据与声明摘要一致，不能独立证明链上存在该记录。若平台不允许匿名查询，不承诺公众可直接独立查询，应提供平台认可的凭证或核验流程，并明确访问要求。

说明文案：存证用于核对该版本资料是否与存证时一致，不代表平台认证产品质量或保证原始填报内容真实。

## 接入前需要确认

1. 企业开通的实际至信链产品、正式与测试环境，以及 SDK/API 文档。
2. 提交、按业务标识查询、回执验证和重复提交的处理方式。
3. 平台实际返回的摘要、交易哈希、存证编号、时间及其语义。
4. 客户是否可以匿名验证，官方验证链接/证书是否可公开分享。
5. 用测试批次完成提交、超时重试、失败、新旧版本、图片篡改及权限测试，再上线。
