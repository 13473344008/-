# T2 — 数据库技术决策

日期：2026-09-07。决策：**选择独立 SQLite，作为第一版后台数据库。** 这是已完成源码核验后的技术推荐；运行可靠性仍需 T4 空库、权限、并发写入和恢复验收，不宣称已通过实测。此次不创建或启动任何数据库。

## 为什么本轮不选 PostgreSQL

少量内部编辑、单个后台实例、扫码端完全不查库，符合 SQLite 的应用形态。所选 Go Admin v2.6.0 有专用 sqlite3 驱动入口、配置、CGO 构建方式、基于 GORM 的初始化和 SQLite 迁移回归测试；Casbin 复用应用 GORM 连接，没有查到必须为 SQLite 重写权限框架的证据。详情和源码链接见 [GO_ADMIN_EVALUATION.md](GO_ADMIN_EVALUATION.md)。

不能把“默认普通构建不带 sqlite3”说成“不支持 SQLite”，也不能把“有测试源码”说成“完整应用可靠性已验收”。本轮未发现明显且必须大量侵入改造的 SQLite 阻断，故没有依据立即增加独立 PostgreSQL 的运维负担。代码生成器仅支持 MySQL 是两候选共同限制，不能作为从 SQLite 改选 PostgreSQL 的理由。

## 比较

| 维度 | SQLite | 独立 PostgreSQL | 本项目判断 |
| --- | --- | --- | --- |
| Go Admin/GORM | sqlite3 标签 + CGO；官方专用配置；迁移有 SQLite 回归源码 | postgres 驱动与初始化分支 | 两者均需 T4 实测；SQLite 启用属于构建配置 |
| RBAC/Casbin | 复用 GORM DB，策略与业务同库 | 同样支持 GORM 持久化 | 角色授权、重启后策略仍需验证 |
| 代码生成器 | 当前 MySQL guard 不通过 | 同样不通过 | 不依赖它生成核心业务 |
| 可靠性 | 本地事务数据库，单写者；需要正确文件系统、短事务和锁等待 | 服务型事务数据库，多会话并发控制 | 不能仅凭少量用户忽略框架日志写入 |
| 并发写入 | 一次只有一个 writer；WAL 不改变这一点 | MVCC、行级锁与事务隔离支持更多并发 | 第一版单实例、发布串行可控 |
| 运维成本 | 无独立 DB 服务、账号网络维护；应用需 CGO 构建 | 增加容器、数据卷、凭据、升级、监控和连接池管理 | SQLite 更低，但不是零维护 |
| Docker | 持久化整个 DB 目录，包括 WAL/SHM；不写容器临时层 | 独立 passport-admin-db 容器及专用卷 | 两者都不接 Directus 数据 |
| 备份 | Online Backup API 或受控停写后安全一致性备份 | pg_dump/pg_restore；需要时物理备份及 WAL/PITR | 必须实际恢复，不只看备份文件存在 |
| 恢复 | 隔离位置恢复 DB、校验完整性、核对资产/发布清单 | 隔离容器恢复，核对版本、权限及数据 | 已发布公开文件在恢复时继续独立服务 |
| 扩展 | 不适合多个主机通过网络文件系统共享写库 | 更适合多实例、重报表、更多并发写者 | 将来达到该需求再迁移 |
| 迁移成本 | 保持核心关系字段及受控 JSON，可编写导出/导入校验 | 类型、序列、SQL 方言需验证 | 不能承诺只改 DSN 即可无损切换 |

SQLite 并发与部署边界依据 [SQLite 适用场景](https://www.sqlite.org/whentouse.html)、[WAL 文档](https://www.sqlite.org/wal.html)；一致性备份依据 [SQLite Backup API](https://www.sqlite.org/backup.html)。PostgreSQL 对比依据 [并发控制](https://www.postgresql.org/docs/18/mvcc.html)、[备份恢复](https://www.postgresql.org/docs/18/backup.html)。资源成本判断是结合本项目架构的工程建议，不是跑分结论。

## SQLite 落地约束（T4 以后实施）

- 单个管理后端实例；使用本地持久磁盘，数据库路径在 passport-admin 独立私有 data 目录；不放在 site、公共静态根、网络共享盘或 Directus 卷。
- 按上游 sqlite3 build tag 和 CGO 编译；macOS 本地、Linux 目标镜像分别验证，不直接跨平台复制二进制。不依赖 Makefile 中未经核验的参数拼写。
- 从空库运行锁定版本全部 migration；禁止复制上游演示 go-admin-db.db 当生产初始化。单独校验迁移记录、系统表、登录、角色与 Casbin 持久化。
- 建议从受控单写连接、短事务、busy timeout 开始；连接池参数通过实际驱动验证。WAL、foreign_keys、busy_timeout 必须检查实际 PRAGMA 结果，保证连接级设置覆盖全部连接。WAL 不是多写者支持。
- 发布引擎先在短事务中冻结输入，之后处理图片与文件；禁止持有写锁等待文件复制或外部请求。并发编辑用修订号冲突检查，避免静默覆盖。
- 框架日志可能异步落库；业务审核/发布审计采用可靠事务记录，不能依赖内存日志队列作为唯一证据。日志轮转、保留期、磁盘阈值要配置。
- 热备份用一致性备份机制，不在运行时只复制 `.db` 而忽略 WAL。备份包括私有资产、不可变发布版本、资产清单与配置恢复说明；密钥单独保护，不放入公开产物。
- 恢复先到隔离目录，做 integrity_check、关系与版本校验、登录和策略核验，再受控替换后台私有库。绝不回退 Directus 或共享数据库。

## T4 必须通过的数据库门槛

1. 在独立本地空目录完成实际应用驱动编译、全量迁移、重复执行，核对实际表与迁移版本；不只依据“初始化成功”日志。
2. 用户/角色/菜单 CRUD、普通角色拒绝未授权请求、Casbin 策略保存后重启仍生效；检查数据权限开启后的过滤行为。
3. 在预期少量用户的并发编辑和日志写入下，无丢写、静默覆盖、未处理的 database locked；记录负载与响应，不编造吞吐目标。
4. 用真实应用驱动完成备份、隔离恢复，验证 DB、资产清单及版本引用一致；不拿 glebarez 单测代替 sqlite3 运行验收。
5. 容器重启不丢数据；磁盘满、只读或权限错误明确失败；不修改任何现有服务器服务。

若这些门槛暴露 SQLite 特有迁移/权限问题且需要大量框架改动，则按用户授权的候选方向调整为 **独立 PostgreSQL `passport-admin-db`**，记录新证据并重新验收，不硬改 SQLite。也可在未来出现多实例并发写或恢复目标要求 PITR 时重新决策。

PostgreSQL 备选只能位于 passport-admin 自身 Compose 的私有内部网络，不接 edge、不映射宿主机公网端口，拥有独立数据卷、账号、备份；禁止连接 directus-db。其具体稳定 PostgreSQL 版本和镜像 digest 在真正启用该备选时核验，本轮不凭空锁定未测试镜像，也不部署服务器。
